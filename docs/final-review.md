# Финальный архитектурный обзор

## 1. Общая оценка архитектуры

Архитектура соответствует масштабу первой стабильной версии AI Personal Learning Platform.

Система разделена на четыре понятных слоя:

- React frontend отвечает за интерфейс и пользовательские сценарии;
- Spring Boot backend отвечает за бизнес-логику, безопасность и координацию операций;
- FastAPI AI-service отвечает только за AI-операции без хранения состояния;
- PostgreSQL хранит основные данные платформы.

Выбранный подход выглядит реалистичным для разработки одним инженером и при этом оставляет пространство для дальнейшего развития.

## 2. Сильные стороны

- `LearningGoal` остается центральной сущностью, поэтому подготовка к экзаменам не превращается в отдельную подсистему.
- Backend владеет бизнес-логикой, проверкой доступа и транзакционными границами.
- AI-service изолирован от PostgreSQL и пользовательской авторизации.
- Backend API версионирован через `/api/v1`.
- Entity не возвращаются наружу напрямую, API строится на DTO.
- PostgreSQL используется как единственное постоянное хранилище.
- Knowledge graph реализуется через обычные таблицы, без графовой БД.
- Graceful degradation описан как контролируемый режим работы, а не как временная заглушка.
- Документация содержит API, БД, безопасность, развертывание, наблюдаемость, политику транзакций, асинхронную обработку и хранение файлов.

## 3. Архитектурные компромиссы

- Модульный монолит выбран вместо микросервисов ради простоты разработки, сопровождения и транзакционной целостности.
- AI-service вынесен отдельно, потому что Python удобнее для AI-интеграций, но бизнес-логика остается в backend.
- Синхронная обработка AI-запросов проще фоновых задач и достаточна для текущего релиза.
- Локальное файловое хранилище проще объектного хранилища и подходит для локальной разработки.
- `masteryScore` рассчитывается простыми объяснимыми правилами вместо ML-модели.
- Knowledge graph хранится как visualization-ready структура, а не как полноценная графовая платформа.

## 4. Ограничения текущего релиза

- OCR и обработка изображений не поддерживаются.
- Извлечение текста из PDF/DOCX/TXT остается упрощенным.
- AI-операции выполняются синхронно.
- JWT может храниться в `localStorage`, что требует осторожности к XSS.
- Полноценные метрики, трассировка и alerting не внедряются.
- Пагинация может быть добавлена постепенно для растущих списков.
- Семантический поиск и pgvector оставлены для следующих версий.

## 5. Почему выбран modular monolith

Modular monolith подходит текущему масштабу системы, потому что:

- дает четкие границы модулей без сетевой сложности микросервисов;
- упрощает транзакции между связанными сущностями;
- снижает стоимость локальной разработки и тестирования;
- позволяет одному разработчику поддерживать всю систему;
- оставляет возможность выделить отдельные сервисы позже, если появится реальная нагрузка или организационная причина.

Ключевое правило: модули должны сохранять внутренние границы и не переносить доменную логику в `common`.

## 6. Почему AI-service без состояния

AI-service не хранит данные и не обращается к PostgreSQL.

Это решение снижает риски:

- нет дублирования бизнес-логики;
- нет отдельной модели доступа в AI-service;
- проще тестировать и заменять AI-провайдера;
- backend остается единственной точкой владения пользовательскими данными;
- AI-service можно масштабировать независимо в будущем.

## 7. Почему синхронная AI-обработка приемлема

Синхронная модель подходит для текущего релиза:

- пользовательский сценарий остается прямым;
- не нужны очереди, фоновые обработчики и статусы фоновых задач;
- проще реализовать обработку ошибок;
- проще проверить сквозной пользовательский сценарий;
- ожидаемая нагрузка и размер материалов позволяют начать без фоновой инфраструктуры.

Риск долгих ответов компенсируется timeout, состоянием загрузки во frontend, `ai_request_logs` и graceful degradation.

## 8. Запланированные расширения

- механизм refresh token с httpOnly cookies;
- объектное хранилище для файлов;
- фоновые задачи для долгих AI-операций;
- пагинация для всех растущих списков;
- метрики и мониторинг;
- embeddings и семантический поиск;
- расширенная аналитика `masteryScore`;
- более надежное извлечение текста из файлов.

## 9. Потенциальные направления масштабирования

- вынести долгие AI-операции в фоновый обработчик;
- добавить очередь задач для обработки материалов;
- заменить локальное файловое хранилище на S3-compatible объектное хранилище;
- добавить endpoints для оптимизированного чтения dashboard при росте данных;
- подключить pgvector для семантического поиска;
- масштабировать AI-service горизонтально, если AI-запросы станут узким местом.

Эти направления не требуют изменения центральной модели `LearningGoal`.

## 10. Основные технические риски

- Невалидные или нестабильные ответы AI-service требуют строгой валидации на стороне backend.
- Большой модуль `learning` может разрастись без дисциплины границ сервисов.
- Упрощенное извлечение текста может давать неполные topics.
- Локальное файловое хранилище требует политики очистки.
- `localStorage` для JWT повышает требования к XSS-защите frontend.
- Синхронные AI-запросы требуют корректных timeout и UX-состояний.
- Простая формула `masteryScore` может потребовать настройки коэффициентов после реального использования.

## 11. Почему архитектура подходит для текущих задач

Архитектура решает основные задачи платформы без избыточности:

- поддерживает заметки, цели, roadmap, tasks, materials, flashcards и отслеживание прогресса;
- сохраняет понятные границы между слоями;
- готова к реализации AI-агентом благодаря явным DTO, endpoints, таблицам и зонам ответственности сервисов;
- учитывает безопасность пользовательских данных;
- описывает операционные аспекты без внедрения тяжелой инфраструктуры;
- остается практичной и расширяемой.

Итоговая оценка: документация готова к архитектурному ревью, технической презентации и пошаговой реализации.
