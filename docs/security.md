# Безопасность

## 1. Назначение

Документ описывает модель безопасности платформы: аутентификацию, авторизацию, хранение секретов, валидацию входных данных и границы доступа между компонентами.

## 2. Жизненный цикл JWT

Пользователь получает JWT после:

- регистрации;
- входа по email и паролю.

Frontend отправляет token в заголовке:

```text
Authorization: Bearer <accessToken>
```

Правила:

- access token имеет ограниченный срок жизни;
- рекомендуемый срок жизни access token для текущего релиза: 15-60 минут;
- backend проверяет подпись и срок действия token;
- backend не хранит access token в БД;
- при `401 Unauthorized` frontend удаляет token и отправляет пользователя на страницу входа;
- механизм refresh token запланирован как будущая стратегия.

JWT должен содержать только минимально необходимые claims: user id, subject, время выпуска и время истечения.

## 3. Хэширование паролей

Пароли не хранятся в открытом виде.

Требования:

- использовать BCrypt через Spring Безопасность;
- хранить только `password_hash`;
- не возвращать hash в API;
- не логировать пароли.

## 4. Модель авторизации

Модель доступа основана на принадлежности данных пользователю.

Каждая пользовательская сущность имеет прямого или косвенного владельца:

- `Note.user_id`;
- `LearningGoal.user_id`;
- `StudyMaterial.user_id`;
- `Topic.user_id`;
- `Task.user_id`;
- `Flashcard.user_id`;
- `KnowledgeNode.user_id`;
- `AiRequestLog.user_id`.

Правило:

```text
currentUser.id == resource.userId
```

Для косвенных ресурсов принадлежность проверяется через `LearningGoal`.

## 5. Проверка принадлежности данных пользователю

Проверка выполняется в слое сервисов.

Repository методы для пользовательских данных должны учитывать владельца:

```text
findByIdAndUserId
findAllByUserId
```

Для доступа к чужому ресурсу предпочтительно возвращать `404 Not Found`, чтобы не раскрывать существование записи.

## 6. Изоляция AI-service

AI-service:

- не имеет пользовательской авторизации;
- не имеет доступа к PostgreSQL;
- не хранит пользовательские данные;
- вызывается только backend;
- должен быть недоступен напрямую из frontend.

В Docker Compose AI-service доступен backend по внутреннему сетевому alias.

## 7. CORS policy

Backend разрешает CORS только для известных frontend origins.

Правила:

- не использовать wildcard `*` для production;
- разрешать только нужные HTTP methods и headers;
- `Authorization` должен быть разрешен как header.

## 8. Стратегия валидации входных данных

Валидация выполняется на request DTO до бизнес-логики.

Правила:

- обязательные поля проверяются через Bean Validation;
- строки проверяются на пустые значения и разумную длину;
- значения enum принимаются только из зафиксированных списков;
- UUID проверяется до обращения к repository;
- размер и тип загружаемого файла проверяются до сохранения;
- frontend validation улучшает UX, но не заменяет валидацию на стороне backend.

Некорректный ввод возвращает `400 Bad Request` в едином формате ошибки.

## 9. Управление секретами

Секреты:

- `JWT_SECRET`;
- database password;
- API key AI-провайдера.

Правила:

- секреты передаются через переменные окружения;
- `.env` не коммитится;
- `.env.example` не содержит реальных значений;
- logs не должны содержать секреты.

## 10. Ограничения localStorage

В текущем frontend JWT может храниться в `localStorage` ради простоты реализации.

Ограничение:

- `localStorage` уязвим при XSS;
- frontend должен избегать небезопасного HTML rendering;
- перед эксплуатацией рекомендуется перейти на httpOnly cookies и механизм refresh token.

## 11. Будущая стратегия refresh token

Будущая стратегия:

- короткоживущий access token;
- refresh token в httpOnly secure cookie;
- endpoint для token refresh;
- rotation refresh token;
- logout с инвалидированием refresh token.

Это не входит в текущий объем, но архитектура auth module должна не мешать такому расширению.
