# Политика транзакций

## 1. Назначение

Документ фиксирует правила работы с транзакциями в Spring Boot backend. Цель - сохранить целостность данных без усложнения архитектуры.

## 2. Общий принцип

Транзакционные границы проходят на уровне service layer.

Controller не открывает транзакции и не содержит бизнес-логику. Repository не координирует сценарии между несколькими таблицами. Service отвечает за атомарность операций и порядок сохранения данных.

## 3. Политика `@Transactional`

Правила:

- `@Transactional` ставится на public methods service-классов, которые изменяют данные;
- операции чтения могут использовать `@Transactional(readOnly = true)`;
- внешние HTTP-вызовы не должны выполняться внутри долгой транзакции, если их можно безопасно вынести до сохранения данных;
- транзакция должна быть короткой и охватывать только работу с БД;
- вложенные транзакции не используются без явной необходимости.

## 4. Границы по модулям

Auth:

- создание пользователя и профиля выполняется атомарно;
- выдача JWT не требует транзакции после успешной проверки пользователя.

Notes:

- создание, обновление и удаление заметки выполняются в одной транзакции;
- проверка принадлежности заметки пользователю выполняется до изменения.

Learning:

- создание `LearningGoal` выполняется атомарно;
- генерация roadmap разделяется на внешний AI-вызов и сохранение результата;
- сохранение `Roadmap`, `RoadmapStep`, `Topic` и связанных `Task` выполняется согласованно.

Tasks:

- изменение статуса задачи и пересчет progress выполняются в одной транзакции;
- обновление `completed_at` происходит вместе со статусом.

Flashcards:

- сохранение `FlashcardReview` и обновление `Topic.masteryScore` выполняются в одной транзакции.

Dashboard:

- dashboard использует read-only операции и не изменяет данные.

## 5. AI request persistence behavior

AI-запросы фиксируются в `ai_request_logs`.

Рекомендуемый порядок:

1. Backend создает запись `ai_request_logs` со статусом `PENDING`.
2. Backend вызывает AI-service вне долгой транзакции бизнес-сущностей.
3. После ответа backend обновляет запись лога статусом `SUCCESS`, `FAILED` или `GRACEFUL_DEGRADATION_USED`.
4. Бизнес-данные сохраняются отдельной короткой транзакцией.

Если AI-service недоступен, ошибка должна быть сохранена в `ai_request_logs`, но существующие данные пользователя не должны повреждаться.

## 6. Стратегия rollback

Rollback выполняется автоматически для unchecked exceptions внутри транзакции service layer.

Правила:

- если не удалось сохранить roadmap, связанные steps и tasks не должны остаться частично созданными;
- если не удалось сохранить `FlashcardReview`, `masteryScore` не обновляется;
- если не удалось обновить статус задачи, progress не пересчитывается;
- ошибки логирования AI-запроса не должны маскировать основную бизнес-ошибку, но должны попадать в backend logs.

## 7. Consistency guarantees

Система гарантирует:

- пользователь не видит частично созданный roadmap;
- task status и progress не расходятся в рамках успешной операции;
- review карточки и изменение `masteryScore` применяются совместно;
- dashboard строится по уже зафиксированным данным.

Система не гарантирует:

- мгновенную доступность результата внешнего AI-провайдера;
- абсолютную точность AI-ответа без валидации на стороне backend;
- распределенные транзакции между backend и AI-service.

## 8. Практическое правило для реализации

Если операция:

- меняет несколько связанных сущностей;
- влияет на progress;
- обновляет `masteryScore`;
- создает roadmap и tasks;

она должна выполняться через service method с явной транзакционной границей.
