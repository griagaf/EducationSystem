# Асинхронная обработка

## 1. Назначение

Документ описывает подход к операциям, которые могут занимать больше обычного API-запроса: генерация roadmap, извлечение topics и генерация flashcards.

В текущем релизе эти операции выполняются синхронно. Это осознанное решение, а не техническое ограничение.

## 2. Текущая модель

Frontend отправляет запрос в backend:

- `POST /api/v1/goals/{id}/generate-roadmap`;
- `POST /api/v1/materials/{id}/extract-topics`;
- `POST /api/v1/goals/{id}/flashcards/generate`.

Backend:

1. Проверяет JWT.
2. Проверяет принадлежность ресурса пользователю.
3. Формирует запрос в AI-service.
4. Получает структурированный JSON.
5. Валидирует результат.
6. Сохраняет данные в PostgreSQL.
7. Возвращает результат frontend.

AI-service остается сервисом без состояния и не хранит очередь задач.

## 3. Почему синхронная обработка приемлема

Синхронная модель подходит для первой стабильной версии, потому что:

- проще реализуется и отлаживается;
- не требует очередей, фоновых обработчиков и отдельной модели статусов фоновых задач;
- делает пользовательский сценарий прямым и понятным;
- снижает количество инфраструктурных компонентов;
- достаточно надежна при ограниченном количестве пользователей и умеренном размере материалов.

## 4. Ограничения синхронной модели

Риски:

- AI-операция может занять несколько секунд;
- frontend должен показывать состояние загрузки;
- backend должен иметь timeout для AI-service;
- большие материалы могут ухудшить время ответа;
- повторные запросы пользователя могут создать дубли, если не проверять состояние.

Минимальные меры:

- timeout на backend client;
- единый формат ошибок;
- запись `ai_request_logs`;
- блокировка повторной генерации, если roadmap уже создан;
- graceful degradation, если внешний AI-провайдер недоступен.

## 5. Границы будущего перехода к async

Переход к фоновой обработке возможен без изменения основной доменной модели.

Потенциальные изменения:

- добавить статус операции генерации;
- вернуть `202 Accepted` вместо готового результата;
- добавить endpoint для получения статуса операции;
- вынести долгие AI-операции в фоновый обработчик;
- хранить промежуточные состояния обработки материалов.

## 6. Что не добавляется сейчас

В текущем релизе не добавляются:

- message broker;
- отдельный сервис фоновой обработки;
- distributed task queue;
- polling API для всех операций;
- WebSocket/SSE уведомления;
- event sourcing.

## 7. Требования к реализации текущего релиза

- Каждая AI-операция должна иметь timeout.
- Frontend должен показывать состояние загрузки и ошибку.
- Backend должен сохранять AI request log.
- Backend должен валидировать AI-ответ до сохранения.
- Повторная операция должна обрабатываться предсказуемо: `409 Conflict` или явная перегенерация, если она будет разрешена в будущем.
